# Sprint 23 Area B: Lattice-aware grid-snap for hex/tri/square

## TL;DR

Do **not** ship either of the two simple lattice-snap variants as specified.
Graphviz dot's lattice outputs are indeed exact integer-grid layouts, but the
sprint-22c LP output is also already grid-quantized in the relevant coordinate
system. The gap is not "LP fractional x noise"; it is the coarser coordinate
assignment produced by `_dot_lattice_lp` relative to dot's network-simplex
placement, especially row offsets and x/rank pitch geometry.

Empirically:

- `hexagonal_lattice_42`: LP is close to dot but still `-0.800` composite. Round
  snapping is a no-op; Hungarian layer snapping regresses by `-3.885` vs LP.
- `triangular_lattice_36`: LP is `-0.479` vs dot, matching the sprint-22 close
  loss. Round snapping regresses by `-12.345` vs LP; Hungarian regresses by
  `-4.453`.
- `grid_5x5`: no-polish Dagua already beats dot by `+2.418`; LP is worse than
  both, and snapping does not recover it.
- Sanity checks (`sierpinski_42`, `planar_60`, `parallel_multiedge_bundle`) do
  not support the simple snap. `sierpinski_42` is especially bad: both variants
  regress hard.

Recommendation: leave sprint-22c `_dot_lattice_lp` unchanged for now. If this
area gets implementation time, spend it on a true dot-style coordinate pass:
integer network-simplex/BK-style x assignment with staggered row offsets and a
small pitch/ranksep validation search, not post-LP rounding.

## Interpretation by graph

`hexagonal_lattice_42` is the only graph where the original intuition mostly
holds. Dot's edge-length CV is much better than LP (`0.099` vs `0.166`), and
the total composite gap is small enough that a coordinate-only finisher could
plausibly close it. However, the observed dot grid has far more distinct x
columns than the LP grid (`18` vs `7`). That means dot is not simply rounding
LP columns to integers; it is placing honeycomb rows on a finer staggered
lattice. The existing LP has a rank pitch near `68` and x pitch near `66`,
which makes diagonal edges substantially longer than near-vertical edges. Dot's
`18`/`72` grid permits smaller row offsets and more uniform local edge lengths.

`triangular_lattice_36` is different. LP already has better edge CV than dot,
and all variants preserve DAG consistency and zero sampled crossing rate. The
remaining dot win appears to come from geometry terms outside plain CV:
straightness and angular layout. The LP's aspect is also very wide (`0.971`)
relative to dot (`0.711`), although raw aspect is not a direct composite term in
`dagua.metrics.composite`. A useful finisher for this graph probably needs
joint x/y geometry tuning, not x-only snapping.

`grid_5x5` is a guardrail against overfitting. The no-polish native layout has
near-zero edge CV and scores `94.014`, ahead of dot at `91.597`. The LP lattice
candidate is not the selected shape here; it scores `89.265`. A new Area B
candidate must therefore remain picker-only and must never be forced for
generic grid DAGs.

`sierpinski_42` shows why the current LP gate is too broad for any blind snap.
The LP itself is close to dot (`-0.514`), but both snap variants damage the
layout severely. This graph is planar and sparse with regular local structure,
so it resembles the target class superficially. The recursive geometry is not a
rectangular/hex/tri lattice, and the snap variants erase useful self-similar
offsets.

`planar_60` and `parallel_multiedge_bundle` do not create a positive case for
the snap. On `planar_60`, LP remains better than dot but worse than the
gradient baseline; snapping is a no-op. On `parallel_multiedge_bundle`, the LP
gate rejects the graph and all candidate outputs are effectively identical.

## Algorithm sketch

Variant 1: global round-to-grid:

```python
def snap_round_global(pos):
    out = pos.clone()
    pitch = median_positive_adjacent_x_gap_by_layer(pos)
    origin = median(pos[:, 0])
    out[:, 0] = round((out[:, 0] - origin) / pitch) * pitch + origin
    return out - out.mean(dim=0)
```

This preserves y and applies a single global integer pitch to all layers. On
hex/grid it is a no-op because LP x values already sit on that pitch. On tri it
collapses distinct LP x values because the global origin and median pitch do not
respect per-layer offsets.

Variant 2: per-layer Hungarian projection:

```python
def snap_hungarian_layer(pos):
    out = pos.clone()
    pitch = median_positive_adjacent_x_gap_by_layer(pos)
    for layer in y_layers(pos):
        idx = nodes_in_layer(layer)
        center = median(out[idx, 0])
        slots = center + pitch * (arange(len(idx)) - (len(idx) - 1) / 2)
        row_ind, col_ind = linear_sum_assignment(abs(out[idx, 0, None] - slots[None, :]))
        out[idx[row_ind], 0] = slots[col_ind]
    return out - out.mean(dim=0)
```

This avoids collisions inside a layer but changes row centers and offsets. It
usually increases edge-length CV or straightness penalty because it destroys
the LP's cross-layer alignment.

The important implementation detail is that these variants deliberately use
only information available to a production polish candidate: the LP output,
`edge_index`, and `node_sizes`. I did not tune against the stored Graphviz
coordinates. A tuned-to-dot projection could obviously improve these six
artifacts, but it would not be a valid in-engine candidate unless the same
parameters were derived from graph structure and then accepted by the picker.

## Risk

The current `_should_dot_lattice_lp` gate returns true for
`hexagonal_lattice_42`, `triangular_lattice_36`, `grid_5x5`, `sierpinski_42`,
and `planar_60`; it returns false for `parallel_multiedge_bundle`.

That gate is too broad for a blind snap candidate. If the snap is only another
candidate inside `_best_of_polish`, the 0.5 composite margin should prevent
actual output regressions. But it would add scoring cost with no measured win.
If the snap were forced after LP, it would regress:

- `triangular_lattice_36`: `-12.345` for round, `-4.453` for Hungarian.
- `sierpinski_42`: `-13.107` for round, `-6.780` for Hungarian.
- `grid_5x5`: `-2.779` for Hungarian, while round is only a no-op.
- `hexagonal_lattice_42`: `-3.885` for Hungarian, while round is a no-op.

The real risk is misdiagnosis: adding a post-LP snap could make us think the dot
gap is addressed while the actual missing piece remains in the x-coordinate
solver.

## Recommended implementation

Do not implement Variant 1 or Variant 2 as sprint-23 production code.

If Area B continues, implement a different candidate:

1. Keep `_dot_lattice_lp` as the seed.
2. Infer layer order from the LP/dummy-expanded ordering.
3. Try a small discrete family of row-offset geometries:
   - normal LP x,
   - half-pitch stagger by rank parity,
   - quarter/third-pitch stagger for honeycomb-like layers,
   - x-pitch and y-ranksep scale pairs near dot's observed ratios.
4. Score each geometry with the existing `_best_of_polish` full-composite
   scorer and require the existing `+0.5` margin.

Gate predicate should be narrower than `_should_dot_lattice_lp`:

- `num_nodes <= 200`
- connected DAG
- median undirected degree between `2` and `4`
- max degree / median degree <= `2.5`
- at least 5 layers
- layer widths regular enough: `max(width) - min(width) <= 3` after ignoring
  singleton boundary layers

Estimated LOC:

- Ship neither simple snap: `0 LOC`.
- Proper staggered lattice geometry candidate: about `180-260 LOC` if it reuses
  `_dot_lattice_lp` output and only validates transformed coordinates.
- True network-simplex integer x with branch-and-bound/tight constraints:
  likely `300-450 LOC` and belongs closer to Area C/A infrastructure than this
  quick finisher.

My call: do not spend sprint-23 implementation budget on simple grid snap. The
remaining `hexagonal_lattice_42` and `triangular_lattice_36` losses are real,
but the measured fix is not rounding; it is a more faithful coordinate
assignment stage.
